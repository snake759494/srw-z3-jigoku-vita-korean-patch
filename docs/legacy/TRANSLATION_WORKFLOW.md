# 번역 원고 정규화와 QA

## 현황 해석

기존 원고는 “셀 채움” 기준으로는 본편 스테이지와 DLC가 모두 완료됐습니다. 그러나 수동 검수 상태와 번역 품질은 별개입니다.

| 범위 | XLSX | 실제 원문 행 | 번역/치환 채움 | 한글 포함 | 원문과 동일 |
|---|---:|---:|---:|---:|---:|
| 스테이지 | 265 | 156,565 | 156,565 / 100% | 147,930 / 94.48% | 6,010 / 3.84% |
| DLC | 77 | 14,181 | 14,181 / 100% | 13,359 / 94.20% | 642 / 4.53% |

스테이지 Google 번역 열은 153,951행(98.33%), DLC는 14,072행(99.23%)이 채워져 있습니다. 이 열은 참고용이며 최종 번역 완료 여부의 기준으로 쓰지 않습니다.

`사전2-flowman.xlsx`의 `검수` 열은 데이터 행 전체가 비어 있습니다. 따라서 현재 상태는 “자동/수작업 번역과 게임용 치환 완료, 공식 수동검수 상태 미기록”으로 보는 것이 정확합니다.

## 기준본 결정

`0_STAGE`와 `01_스테이지 xlsx 모음`에는 동일한 이름의 XLSX 265개가 중복됩니다.

- 242개: SHA-256까지 동일
- 23개: XLSX 패키지 바이트는 다르지만 첫 시트의 값과 수식은 좌표별로 동일

번역 셀 검수용 기준본은 모아 보기 쉬운 `01_스테이지 xlsx 모음`을 권장합니다. 다만 평탄화된 모음이므로 asset provenance와 빌드 입력의 단독 기준은 아닙니다. `0_STAGE`의 원래 폴더 문맥과 CPK 엔트리/해시 매니페스트를 함께 보존해야 하며, 새 저장소에는 XLSX 두 벌을 동시에 넣지 않습니다.

파일명과 시트명이 어긋난 사례도 있습니다. `STG0001a(1화)-ID00004-script-통합.xlsx`의 첫 시트는 선행 공백이 포함된 ` ID00003`입니다. 새 추출기는 파일명이나 시트명만 믿지 말고 CPK 엔트리 ID와 원본 해시를 함께 사용해야 합니다.

## 정규 TSV 스키마

XLSX는 검수 UI로 유지할 수 있지만 저장소의 기준 데이터는 UTF-8 TSV를 권장합니다.

| 필드 | 설명 |
|---|---|
| `entry_id` | `STG0001a/ID00003/000065` 형태의 불변 ID |
| `asset_path` | 원본 CPK/BIN과 내부 엔트리 경로 |
| `source_sha256` | 추출 대상 원본 payload 해시 |
| `source_offset` | 원본 payload 시작 기준 0-based 바이트 오프셋. XLSX의 16진 주소는 정수로 변환하며 주소가 없으면 `null` |
| `source_text` | 변경하지 않은 일본어 원문 |
| `translation` | 사람이 읽는 최종 한국어 |
| `replacement_text` | 게임 문자표로 치환된 삽입 문자열 |
| `encoding_profile` | 대상별 문자 인코딩/TBL 프로필 ID |
| `mapping_sha256` | 사용한 TBL/치환표의 SHA-256 |
| `byte_limit` | 대상 필드의 허용 바이트 수 |
| `encoded_length` | 선택 문자표로 인코딩한 실제 바이트 수 |
| `control_signature` | 제어 토큰을 출현 순서대로 담은 공백 없는 JSON 배열 문자열. 토큰이 없으면 `[]` |
| `status` | `draft`, `review`, `approved`, `blocked`, `unchanged-ok` |
| `reviewer`, `notes` | 검수 기록과 예외 사유 |

Google/웹/Gemini 번역은 별도 참고 열이나 provenance 테이블로 보존하되 `translation`과 혼동하지 않습니다.

`approved`와 `unchanged-ok`는 배포 허용 상태입니다. 두 상태의 행은 비어 있지 않은 `reviewer`와 `null`이 아닌 `encoded_length`를 반드시 가져야 하며, 모든 행은 사용한 `encoding_profile`과 `mapping_sha256`을 기록해야 합니다.

## 필수 QA

1. `entry_id`의 중복·누락과 추출/삽입 행 수 일치
2. `⑲`, `⑳`, `㊥`, `㊦`, `㊧`, `㊨` 등 게임 제어 토큰의 순서·개수 보존
3. 선택 TBL에 없는 문자와 대체문자 탐지
4. CP932/사용자 문자표로 계산한 실제 바이트 길이 초과
5. 빈 번역, 원문 동일, 일본어 잔존, 한글 미포함 행의 사유 분류
6. 용어집 위반과 같은 원문의 번역 불일치
7. CPK 엔트리 ID, 파일명, 시트명, 주소의 상호 일치
8. 승인 상태 없는 행을 차단하고, 배포 허용 행의 검수자·인코딩 길이·문자표 해시를 재검증

원문 동일 행은 모두 오류가 아닙니다. 숫자, 기호, 고유명, 제어문일 수 있으므로 자동 삭제 대신 `unchanged-ok` 또는 `review`로 분류합니다.

검사는 `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Test-Translations.ps1`로 실행합니다. 기본 입력 `translations/normalized` 또는 `-TranslationRoot` 아래에 TSV가 없으면 실패합니다. 문자표 매핑 파일 형식은 아직 확정되지 않았으므로 배포 허용 행을 검사할 때는 문자표 미수록 여부를 판정하는 `-ProfileResolverPath`를 반드시 지정하며, 없으면 `[검사 불가/차단]`으로 처리합니다. 해석기 계약은 `tests/README.md`에 기록합니다.

## 사전 통합

- `dictionary.txt`: 1,402개의 `일본어=한국어` 쌍
- `template-시옥편AI번역DIC.txt`: 사전 약 1,430행과 AI 프롬프트/보존 규칙이 혼재
- `사전2.xlsx`: 정리본 4,464개 데이터행, 추가 사전 3,167쌍
- `사전2-flowman.xlsx`: 검수 표식 0개

새 프로젝트에서는 용어 데이터와 AI 프롬프트를 분리합니다. 용어집은 `source`, `target`, `category`, `scope`, `status`, `notes` 열을 가진 TSV로 만들고, 프롬프트는 코드/설정으로 별도 버전관리합니다.

## 문자표와 폰트

기존 일반 `.wReplace`는 한글을 CJK 코드 위치로 바꾸는 2,353개 한글 매핑을 포함하고 `(oper)`판은 2,350개입니다. `폰트/한글문자열.txt` 기준 파일의 고유 완성형 한글 음절도 2,350자입니다. 이 수치는 전체 실시간 번역문을 다시 집계한 값이 아니라 폰트 제작 기준 파일의 값입니다. 두 WReplace 판은 전체 네 항목이 다르므로 암묵적으로 섞지 말고 문자표 버전을 자산별로 고정합니다.

TBL은 237개 파일이지만 실제 내용은 16종입니다. 특히 제어 토큰이 들어간 `shift-jis.tbl`, `shift-jis2.tbl`, `shift-jis-ex.tbl`의 역할을 분리해 해시로 식별해야 합니다.

검사한 주요 글꼴 후보는 필요한 2,350음절을 모두 포함하지만, 포함 여부와 재배포 허가는 별개입니다. 최종 사용 글꼴의 이름, 버전, 원본 URL, 라이선스, 수정 여부를 `fonts.lock.json`에 기록하기 전에는 바이너리를 저장소나 배포본에 넣지 않습니다.

## 텍스처 정리

최종 후보 `1_PCSG00264_Korean`에는 판독 가능한 PNG 230개가 있으나 고유 해시는 225개입니다. 완전히 같은 `- 복사본` 계열 5쌍은 매니페스트에서 비사용임을 확인한 뒤 정규 자산 후보에서 제외하되, 원본 읽기 전용 스냅숏에서는 삭제하지 않습니다. 작업 폴더와 공통 이름 218개 중 185개는 파일 바이트가 달라 단순히 최신 시각만으로 선택하면 안 됩니다.

필요한 매니페스트 필드:

- Vita3K 텍스처 해시 파일명
- 원본 GXT/CPK/엔트리 ID
- 원본·수정 PNG SHA-256와 크기/색상 형식
- 편집 소스와 사용 글꼴
- 검수 화면/메뉴 위치
- 상태와 라이선스
